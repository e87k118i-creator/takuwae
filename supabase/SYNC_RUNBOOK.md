# v2.1 同期候補：認証待ちの間に完了した作業（2026-11-22）

## 有効範囲

開発先は `feature/sync-v2.1.0`。この変更は本番 `index.html` / `sw.js` / `main` を変更しない。
DBマイグレーションの実行、実アカウントの家計データの読取・移行・書込、認証メール送信は行っていない。
公開済みの読み取り専用認証サイトにも、この同期エンジンを配備していない。

## 実装したもの

| ファイル | 役割 |
|---|---|
| `sync-engine.js` | 所有者別の永続ジャーナル。初回受信、初回登録の準備、編集保存、再送、競合停止・手動解決 |
| `sync-merge.js` | 共通の受信済みデータを基準にした三者比較。独立した追加を保持。同じ内容の衝突は停止 |
| `sync-session.js` | 認証済みアカウントとの接続部品。デフォルト読み取り専用。書込には別の明示操作が必須 |
| `sync-demo-server.js` | ネットワークを使わない架空サーバー。原子的応答と同一ID再送を再現 |
| `../sync-simulator.html` | A/Bの編集、オフライン、応答紛失、再起動、競合を試す架空データ画面 |
| `../sync-candidate.html` | 現行本体UIを架空データで動かし、保存・受信を同期エンジンにつなぐ候補画面 |

`sync-candidate.html` は `index.html` のソースから画面を組み立てるが、本番の保存データは取得しない。
初期読取・保存を候補専用のメモリー内保存へ置換する。元の保存コードの形が変わった場合は起動を拒否する。
PWA登録、JSON取込、本番更新操作を止める。これは実際の端末保存とAuthを接続したリリース版ではない。

## 保存と送信の規約

- ジャーナルキーは `takuwae-sync-v2.1-journal:<ownerId>`。旧保存キーには触れない。
- `edit(fn)` は最新状態を排他取得し、同期的に編集し、保存成功後に完了する。
- フォーム全体の保存は `saveLocal(next, {expectedLocalDb})`。表示後に他タブが更新していたら拒否する。
- Web Locksなどの `withLock` を必ず注入し、編集と送受信を同じ排他範囲に置く。
- 画面は保存Promiseを待ち、成功前に「保存済み」と表示しない。候補UIは保存中の追加操作を止める。
- 不明な通信結果では、未送信のバッチID・内容を変えずに保持する。受領済みの再送は既存RPCのreceiptで重複排除する設計。
- 応答の件数・キー・版番号・削除状態を照合し、確認できるまで未送信を削除しない。
- 初回登録は外部バックアップと確認文を必須にし、登録後の本文・件数照合に失敗したら停止する。
- 初回受信先に保存済みジャーナルがあれば上書きしない。クラウドが空なら送信も受信上書きもしない。
- 競合は双方を外部退避したうえで手動解決。確認後にサーバーが変わっていた場合は再確認を要求する。
- ログインと書き込み解禁は別。`createSyncSession` はログイン後も読み取り専用。
- `close()` / `pauseWrites()` 後は新しい送信を開始しない。開始済みHTTPのサーバー確定を取り消す機能はない。

## 検証結果

実行: `cd supabase && npm test`（実際には端末付属のNode v24.22.1で `node --test supabase/*.test.mjs`）。
2026-11-22時点で33テストすべて成功。従来のテストファイル5本もこの中に含む。
CIはNode 22で同じテストを実行する設定。ローカル成功とCI結果は区別する。

確認したケース: 初回受信保護、明示初回登録、2端末の独立追加、同一レコード競合、削除対編集、
通信断・再起動、成功後の応答紛失、追加編集後の再送、保存容量不足、ACK保存失敗、版番号競合、
不正応答、所有者不一致、破損ジャーナル、改変されたバッチ、削除・復元、複数タブの古いフォーム、
同時編集の直列化、初回登録の照合不一致、振替・積立・支出の金額維持、未積立月のzero維持、
読み取り専用の接続、受信の件数不足、429エラー表示。

ブラウザで確認:
- `sync-simulator.html`: A/Bの独立追加をA→B→Aで同期し、両方の取引が残る。
- 同じ予備枠をA/Bで異なる金額へ変更し、Bは競合停止。サーバー値とBの編集値を両方保持。
- `sync-candidate.html`: 本体UIのちょい記録でAに架空の100円支出を保存し、A→B同期後、Bの履歴に同額が現れる。

## 実認証後に残るゲート

1. 本人のアカウントで認証完了・再ログイン・トークン期限切れを確認する。送信制限中はメールを送らない。
2. `sync-session.js` を隔離した実認証候補へ接続し、実環境のCORS、HEAD/GET、RLS、Web Locks、iOS保存を確認。
   現行の公開認証ラボは件数確認だけのまま維持する。
3. 別の明示承認を得た検証用レコードで、RPCの競合・二重送信・原子性・別ユーザー隔離を実測する。
   今回は実サーバーへ検証データも書き込んでいない。
4. 本体の全保存経路を候補へ接続する。候補画面で主要経路は接続実証したが、実ストレージ・Auth版は未接続。
   対象: ちょい記録、通常入出金、給与、固定費の状態・精算、積立・取崩、履歴訂正・取消、各種設定。
   `month()` / `billState()` は描画でも空の月次状態を作るため、表示だけの変更を勝手に送信しないよう区別する。
5. 本体の復元・初期化は同期中の一括削除につながるため、そのまま許可しない。専用の退避・確認導線が必要。
6. iPhone正本の外部JSONバックアップ確認→明示初回登録→内容照合→iPad初回受信→残高等の照合。
7. オンライン復帰・画面復帰での同期トリガー、認証更新、競合確認UIを実端末で検証後、本番公開を判断する。

## 意図的な停止条件

- 1回の操作は250レコード / 1MiB以内。複合家計操作を勝手に分割して一部だけ反映しない。
- 受信は単一GETで最大1000レコード（削除済みを含む）。全件数と取得件数が合わない場合は停止。
  複数ページは更新時点が混ざるため使用しない。上限を超える運用には別途スナップショットAPIが必要。
- 同じ設定オブジェクト（例: 初期残高）を両端末が別々に変更した場合も、保守的に競合停止する。
- `closing` / `rollover` の独立レコードは現行codecで復元を定義していないため、無視せず受信を停止する。
- 日常的な認証トークンの自動更新・安全な保持、バックグラウンド常時同期は未実装。

## ロールバック

本番は旧保存のままなので、候補で問題が起きたら候補を閉じる。旧保存キー、main、PWAキャッシュを削除しない。
実環境を後で有効化した場合はまず送信を停止し、ローカル・クラウド双方を退避する。
競合や不明な送信結果があるジャーナルは削除せず、同じバッチIDで照会・再送できる状態を保つ。
